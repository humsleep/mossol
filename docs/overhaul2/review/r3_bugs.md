## 2. 새로 확인한 문제 없음(통과 항목)

### 2.1 세이브 호환 — 출시판(HEAD) 실제 세이브

`git worktree` 로 HEAD 를 꺼내 **출시판 코드로 직접 플레이해** SharedPreferences 를 통째로 떠 왔다(`r3_scripts/live_dumps/*.json`, 만든 스크립트 `zz_r3_head_dump_test`).

- `veteran_mid_1~3`: 2회 엔딩 뒤 3회차 D5 이벤트 도중.
- `newbie_mid`: 1회차 D3 이벤트 도중.
- `veteran_morning`: 엔딩 1회 뒤 2회차 D11 아침.
- `veteran_after_ending`: 엔딩 직후, 세이브 없음.

각 덤프를 이번 브랜치에서 `init` → `continueGame` → 엔딩까지 무작위로 플레이했다. 결과:

- 예외 0, 빈 이벤트 0, 모두 엔딩에 닿는다. 새 필드(`todayCliffhanger`·`todayCliffRank`·`chainRank`·`dayClockEnd`)는 없으면 null/빈 값으로 읽힌다.
- 이전(마이그레이션):
  - 엔딩이 있으면 `completedStarts=[classic]` 이고, `startEndings.classic` 은 앨범과 같다.
  - `totalRuns > 1` 이면 `seenEvents` 는 지금 세이브의 `seen` 과 같다.
  - `newbie_mid`(totalRuns 1, 엔딩 없음)는 아무것도 채우지 않는다.
- 다음 회차를 `sc_leak` 로 시작하면 `veteran`·`done_classic` 이 선다.
- **멱등**: 같은 기기를 두 번 실행해도 메타 JSON 이 바이트 단위로 같다.

### 2.2 세이브 호환 — 이번 브랜치의 이전 형태

R1 시기 세이브(새 하루 필드 4개가 아예 없음)와 그 4개가 명시적 `null` 인 세이브를 만들었다. 두 경우 모두 하루 도중 이어 하기 → 엔딩까지 예외가 없다.

### 2.3 마이그레이션 반복·손상 앨범

앨범 `['solo_strong', 'gone_ending', 'solo_strong', '']`, `totalRuns 5` 로 세 번 실행했다.

- 매번 `completedStarts=[classic]` 이다. 중복은 접히고, 빈 id 는 다시 읽을 때 `_strs` 가 버린다.
- 없는 엔딩 id 는 `startEndings` 에 남는다. 앨범 자체가 그 id 를 이미 세고 있으므로(`distinctEndingCount`) 새 문제가 아니다.
- 메타 JSON 이 깨지면 `load()` 가 메타를 지운다(이전부터의 동작). 다음 실행에서 앨범으로 다시 채워진다.

### 2.4 되돌리기 스냅샷(메모리)

사슬 선택 → 되돌리기 → 다른 선택을 해 봤다. 아래는 모두 선택 직전 값으로 돌아온다.

- 큐.
- 사슬 순위(`chainRank`).
- 클리프행어.
- `dayClockEnd`.

다른 선택 뒤 재시작해도 `x` 가 다음, 예고 `M` 이다. 시뮬(§4)에서 되돌리기 4,895번을 섞어도 불변식 위반이 없다. **디스크에 남는 값은 R3-1.**

### 2.5 변형 본 기록(`id#번호`) 결정성

실제 데이터로 시작 6종 × 시드를 돌렸다. 이벤트 도중 약 10% 확률로 앱을 다시 켰다.

- 화면에 실제로 뜬 변형 키(361개)와 `_absorbSeen` 이 메타에 적은 키를 비교했다. **불일치 0**이다.
- 2회차 40일 동안 `canFastForward` 가 참인데 그 변형을 실제로 본 적이 없는 경우도 **0/85**다.

### 2.6 메타 크기

시작 6종 × 성별 2 = 12판을 끝까지 했다. 메타는 5.2KB → 14.9KB 다.

- `seenEvents` 652개(변형 키 96개), `seenRipples` 191개.
- 상한은 이벤트 646개 + 변형 키 102개다. 파급 줄을 더해도 25KB 안팎에서 멈춘다. SharedPreferences 한계와는 거리가 멀다.

### 2.7 진상 칩 레이아웃

320×568, 배율 1.0·1.3·2.0·3.0, 라이트·다크에서 그리고 끝까지 굴렸다.

- 대상:
  - 행동 화면: 소문 0/95 + 진상 12.
  - 정산: 소문 99 (−12) + 진상 12 (+3).
  - 결과 패널: 진상 선택.
- 행동·정산은 넘침 0건이다. 칩은 화면 안에 있고 말줄임도 없다.
- 2.0 에서는 게이지(20..264)가 한 줄을 다 쓰고, 칩이 다음 줄로 내려간다.
- 결과 패널은 2.0 까지 0건이다. 3.0 의 넘침은 진상 칩이 아니다(범위 밖 1).
- 색 단계 8개(라이트 4·다크 4)의 글자/바탕 대비는 6.57 ~ 16.38 이다. 모두 WCAG AA(4.5) 이상이다.

### 2.8 빨리 감기·탭 공개 경쟁 상태

대상은 이전 회차에서 본 장면이고, 대사·대기 20초·대사 순서다.

- **한 프레임에 탭 5번**: 대기 줄 바로 앞(3번)에서 멈춘다.
- **대기 중 30ms 간격 탭 5번**: 대기를 넘지 않는다.
- **무료 건너뛰기와 대화 탭을 같은 프레임에**: 남은 줄이 다 열린다. 자존감 대가가 없다(정상).
- **대기가 자연히 끝나는 동안 500ms 마다 탭**: 대가가 정확히 −1, 한 번이다.
- **선택지가 뜬 뒤 탭, 반응 중 탭**: 아무 일도 없다(`lastOutcome` 가드).
- **통화 장면**:
  - 통화 화면에는 `chat-tap` 이 없다(0개). 빨리 감기는 줄 간격만 줄인다.
  - 울리는 중·알림 카드 중에는 대화 영역이 아예 그려지지 않는다. 그래서 탭으로 몰래 공개되는 경로가 없다.
- **미니게임**: 대사가 끝난 뒤(`linesDone`) 별도 라우트로 뜬다. 탭 처리는 그 시점에 아무것도 하지 않는다.

### 2.9 분석 이중 기록

- `run_started` 는 새 게임마다 정확히 1번이다.
- 온보딩 `start` 단계는 인트로(`_loggedStart`)·홈(`isFirstOnboarding`) 모두 한 흐름에 한 번이다.
- `wait_skip_free` 는 탭 1번에 1번이다. 예외는 R3-3 이다.
- 광고 `wait_skip` 경로는 `RewardedButton` 쪽에서만 기록하므로 무료 건너뛰기와 겹치지 않는다.

### 2.10 `characters.json` `firstLine`

죽은 데이터가 아니다. 경로는 다음과 같다.

- `CharacterDef.fromJson` 이 `firstLine` 을 읽는다(models.dart:1215, 빈 문자열은 null).
- `StoryBundle.rawFirstLineOf` 가 그것을 루트 이벤트의 첫 대사보다 **먼저** 쓴다(story_repository.dart:112).

- 출시 검증에서도 자리표시자를 검사한다(story_repository.dart:327).
- 지금 6명에 들어 있다.

## 3. 새로 찾은 문제

### P2

#### R3-1. 되돌리기가 디스크에 저장되지 않는다 — 앱을 끄면 광고로 산 되돌리기가 사라지고, 하루 필드도 선택 뒤 값으로 돌아온다

- **위치**: `lib/game_controller.dart` `undoChoice()`(약 1680~1750행). 메모리 상태는 모두 되돌리지만 `_save(s)` 를 부르지 않는다. 선택 때 `_apply` 가 저장한 "선택 뒤" 세이브가 그대로 디스크에 남는다.
- **재현**: `zz_r3_engine_test` `undo with the r2 day fields` 두 건.
  - `m1` 에서 A(매력 −5, `next: h1`) → (광고 시간만큼 기다림) → 되돌리기 → 그 자리에서 앱을 다시 켠다.
  - 디스크: `seen=[m1]`, `dayQueue=[h1, x]`, `todayCliffhanger=M`, `chainRank={h1: 0}`(선택 뒤 값).
  - 다시 켠 뒤: `current=x`(또는 `h1`). `m1` 이 사라지고 매력은 10 → **5**(되돌린 선택의 효과가 남는다).
- **영향**:
  - 리워드 광고를 보고 되돌린 직후 앱을 끄거나, OS 가 앱을 죽이면 되돌리기가 없던 일이 된다.
  - 이번에 새로 저장하는 하루 필드(사슬 순위·예고·시계)도 같이 선택 뒤 값으로 돌아온다. 그래서 "되돌리기가 큐·순위·시계를 되살린다"(E9)가 재시작을 건너서는 지켜지지 않는다.
  - 다시 고르기 전에 끊길 때만 생긴다. 다시 고르면 `_apply` 가 새로 저장하므로 문제가 사라진다.
- **원인 시점**: HEAD 의 `undoChoice` 에도 `_save` 가 없다(이전부터 있던 문제). 다만 E9 로 되돌리는 범위가 넓어져 피해도 넓어졌다.
- **제안**: `undoChoice()` 끝(`notifyListeners()` 앞)에서 `_save(s)` 를 부른다. 그 시점에는 `lastOutcome == null` 이므로 `dayQueue` 맨 앞에 지금 이벤트가 다시 들어가고, 하루 필드도 메모리 값(되돌린 값)으로 써진다. 회귀 테스트는 위 스크립트의 "after relaunch" 기대값을 `current=m1, charm=10` 으로 바꿔 쓴다.

#### R3-2. `run_started` 의 `fate:1` 이 부풀려진다 — 운명이 엔딩 전까지 남아 있어서(E8 부작용)

- **위치**: `lib/game_controller.dart` `newGame`: `final fate = m?.pendingFate == startId;`
- **원인**: E8 로 `pendingFate` 는 그 시작으로 엔딩에 닿을 때까지 지워지지 않는다. 그래서 "운명 카드로 시작했는가"가 아니라 "지금 시작이 남아 있는 운명과 같은가"를 센다.
- **재현**: `zz_r3_engine_test` `analytics`. 아래 순서로 새 게임을 4번 했다.
  1. 운명 `sc_leak` 을 뽑고 `sc_leak` 시작.
  2. 버리고 다시 `sc_leak`.
  3. `classic`.
  4. 다시 `sc_leak`.

  `fate` 값이 `[1, 1, 0, 1]` 이다. 운명 뽑기는 1번인데 `fate:1` 회차가 3번이다.
- **영향**: 01_design §7.4-2 의 "운명 뽑기 효과" 판단 지표가 부풀려진다. 운명 시작에서 이탈했다가 다시 시작하는 사람이 많을수록, 운명 회차 수가 과대 집계된다. 그러면 운명 회차의 완주율·D7 이 과소 집계된다. 게임 진행에는 영향이 없다.
- **제안**(택1):
  - 시작 시트가 "운명 카드로 골랐는지"를 `newGame(viaFate: true)` 로 넘기고 그것을 기록한다.
  - 메타에 `fateRunStarted` 를 두어 같은 `pendingFate` 로는 처음 한 번만 `fate:1` 로 센다.

### P3

#### R3-3. 무료 건너뛰기를 한 프레임에 두 번 누르면 두 줄이 넘어가고 `wait_skip_free` 가 두 번 남는다

- **위치**: `lib/ui/event_screen.dart` `_skipWaitFree()` → `_skipWaitEarned()`. 대기 중인지(`_waitLeft > 0`) 확인하지 않고 `revealNext()` 를 부른다.
- **재현**: `zz_r3_ui_test` `free-skip double tap in ONE frame`. 같은 프레임에 두 번 탭하면 `revealed 3 → 5` 이고 기록이 2건이다. 60ms 간격이면 버튼이 이미 사라져 1번만 된다(R2 확인).
- **영향**: 두 손가락으로 거의 동시에 눌러야 생긴다.
  - 넘어간 줄은 지워지지 않고 바로 보일 뿐이다.
  - 다만 그 다음 줄이 또 대기 줄이면 그 대기도 공짜로 넘어간다.
  - 측정은 1건이 더 남는다.
- **제안**: `_skipWaitFree` 첫 줄에 `if (!mounted || _waitLeft <= 0) return;` 를 넣는다. 광고 경로 `_skipWaitEarned` 도 같은 가드를 두면 안전하다.
