## 1. `lib/audio/sfx_service.dart` — 큐 요청 (기존 요청 보강 + 새것 하나)

`docs/review/12_audio_handoff.md` §1 이 이미 네 개(`tap_bad`·`undo`·`timer_low`·`step`)를
요청해 뒀다. **그 네 개를 그대로 지지한다.** 갈아 끼울 지점은 여전히 `MinigameSfx` 한
클래스 안에 모여 있다(`lib/minigames/minigame.dart`). 두 건에 근거를 더하고, 새로 하나를 낸다.

### 1-1. `tap_bad` — 지금 무음인 것을 확인했고, 무음으로 둔 판단은 맞다

`choiceFail` 을 빌리면 "졌다" 와 "틀렸다" 가 같은 소리가 되어 **결과 구별이 망가진다.**
남은 큐 중 뜻이 맞는 것이 없다(`msgOut` = 내가 보냈다 / `waitRead` = 전진 큐 그 자체 /
`callEnd` = 통화). **뜻 없는 큐를 빌리는 것보다 무음이 낫다** — 그 판단에 동의한다.

다만 "진동만" 이 최종 답이 되면 안 되는 이유를 하나 얹는다. **진동은 두 겹으로 꺼진다** —
앱 토글, 그리고 iOS 시스템 진동(이건 앱 토글과 무관하게 `HapticFeedback` 을 무력화한다).
그러면 헛디딤의 채널이 화면 하나뿐이 된다. `nudge()` 8곳을 전부 열어 화면이 무엇으로
대답하는지 확인했고(판정표는 13_minigame_fixes §3-2), **일곱 곳은 화면이 충분히 말한다.
모자랐던 한 곳(맞장구의 놓친 박자)은 내 파일에서 화면으로 고쳤다** — 소리 없이.
그러니 이 요청은 급하지 않다. 다만 `tap_bad` 가 생기면 화면만으로 버티는 자리들이
다 편해진다.

### 1-2. `timer_low` — 문서가 고정한 "판당 한 번" 이 표정 읽기에서는 최대 4번이다

`12_audio_fixes.md` §1 표가 `timeLow()` 를 "**판당 한 번**" 으로 적었는데, 코드는 30%
경계를 다시 올라가면 재장전되고 **표정 읽기는 문제마다 시계를 되감는다.** 그래서 한 판에
**최대 4번** 난다. 동작 자체는 옳다(문제마다 제 시계가 있다). 어긋난 건 문서의 불변식이고,
그 문서는 내 소유가 아니라 고치지 않았다 — **`12_audio_fixes.md` §1 의 그 칸을
"판당 한 번(표정 읽기는 문제마다 되감으므로 최대 4번)" 으로 고쳐 주세요.**

그리고 그 큐가 `callEnd`(통화 종료음, P1)라서, 전화 화면에서 그 소리를 배운 플레이어는
표정 읽기 **한 판에서 "통화가 끊겼다" 를 네 번 듣는다.** `timer_low` 가 필요한 이유가
"뜻이 어긋난다" 에서 "한 판에 네 번 어긋난다" 로 올라갔다.

### 1-3. **새 요청** — 크리티컬 전용 큐, 또는 `choiceOk` 와 짝이 되는 상위 큐

글자를 안 읽고 세 결과를 구별할 수 있는지 봤더니 **성공 vs 크리티컬이 안 갈린다.**

| | 소리 | 진동 | 화면 |
|---|---|---|---|
| 성공 | `choiceOk` | `medium` | `surfaceContainerHigh` + success 배지 |
| 크리티컬 | **`choiceOk` — 같은 파일** | `medium` + 90ms 뒤 `heavy` | `primaryContainer` + brand 배지 |

즉 **진동을 끈 플레이어에게 크리티컬은 성공과 소리로 완전히 같다.** 남는 비-글자 신호는
바탕색 하나다. 게임이 주는 가장 좋은 결과가 가장 약하게 말하고 있다.

| 요청 큐 id | 상황 | 지금 | 제안 규격 |
|---|---|---|---|
| `choice_crit` | 미니게임/선택의 **크리티컬** 판정 | `choiceOk` 와 같은 파일 + 진동 한 번 더 | 0.4s · P1 · `choice_ok` 와 **같은 음색에 한 음 위**(형제로 들려야 한다. 전혀 다른 소리면 "성공의 상위" 로 안 읽힌다) · `medium` |

미니게임 쪽 갈아 끼울 자리는 한 줄이다 — `MinigameSfx.result()` 의
`_s.cue(r.success ? Sfx.choiceOk : Sfx.choiceFail)`. 큐가 생기면
`r.critical ? Sfx.choiceCrit : …` 로 바꾸고 90ms 둘째 박자는 그대로 두면 된다.
**큐가 없는 동안에는 이 자리를 건드리지 않는다** — 뜻이 어긋난 큐를 빌려 오면
성공/실패 구별까지 흐려진다.

## 2. `lib/ui/event_screen.dart:381` — **(B) 로 가 주세요.** 성패음 중복은 남길 것이 아니다

`12_audio_handoff.md` §2 가 (A) 그대로 / (B) 미니게임을 거쳤으면 건너뛰기 / (C) 더 낮은
큐로 세 갈래를 남기고 (A) 로 뒀다. 저자가 아닌 사람으로서 다시 보고 **(B)** 를 권한다.
근거 셋(자세한 것은 13_minigame_fixes §3-3):

1. **둘째 소리에 새 정보가 0 이다.** `event_screen.dart:1177` → `game_controller.dart:1462`
   (`forcedSuccess`) → `event_engine.dart:578` 로 따라가 보면 **둘째 큐의 성패는 첫째 큐가
   이미 결정해 둔 값**이다. 다를 수가 없다. 1.5초 전 소리로 100% 예측되는 소리는 두 번째
   박자가 아니라 메아리다.
2. **1.5초는 두 박자로 안 읽힌다.** 이 저장소의 두 박자 어법은 90ms(크리티컬)·120ms(엔딩)다.
   1.5초는 그 열 배 넘고, 사이에 전면 라우트 전환이 끼어 장면도 끊긴다.
3. **회차당 150판.** 가장 많이 듣는 소리를 두 배로 만드는 것이고, 효과음 토글을 내리게
   만드는 가장 빠른 길이다. 그 토글은 전역이라 **나머지 10개 큐까지 함께 잃는다.**

**미니게임 쪽을 남기고 채팅 쪽을 건너뛰는 이유**: 미니게임의 결과 큐가 ① 플레이어 자기
손이 만든 판정의 순간에 나고, ② 크리티컬을 구별하는 유일한 청·촉각 신호(90ms 뒤 `heavy`)를
들고 있고, ③ 12종이 공유하는 한 자리라 빠뜨릴 수가 없다. 채팅 큐가 알리는 상태 변화는
답장 글과 수치 변화로 이미 읽힌다.

**(C) 를 뺀 이유**: 큐를 낮춰도 "정보 없는 소리를 1.5초 뒤에 한 번 더" 라는 성질이 그대로다.

### 고칠 자리 — 같은 줄에 이미 선례가 있다

`_syncReply()` 는 이미 거절을 건너뛴다. 조건 하나를 같은 모양으로 더하면 끝난다.

```dart
// 지금 (event_screen.dart:380-382)
if (o != null && c.lastChoice?.decline != true) {
  _sfx.cue(o.success ? Sfx.choiceOk : Sfx.choiceFail);
}

// 제안 — 미니게임이 판정한 결과면 MinigameScaffold 가 이미 냈다(1.5초 전).
if (o != null &&
    c.lastChoice?.decline != true &&
    c.lastChoice?.minigame == null) {
  _sfx.cue(o.success ? Sfx.choiceOk : Sfx.choiceFail);
}
```

**`minigameNote` 로 판별하지 마세요.** `MinigameResult.message` 는 비어 있을 수 있어서
(`message` 기본값이 `''`) 조건이 조용히 새는 자리가 생긴다. `lastChoice?.minigame` 은
**선택지 정의** 에 있는 값이라 결과와 무관하게 언제나 맞다.
자유 입력 경로(`confirmFree`)도 같은 `_lastChoice` 를 채우므로 한 줄로 둘 다 덮인다.

시험은 그쪽 소유(`test/widget/**`)다. 제안: 미니게임 붙은 선택지를 하나 끝내고
`RecordingSfxService.played` 에 `choiceOk` 가 **한 번만** 있는지, 그리고 미니게임 없는
선택지에서는 여전히 한 번 나는지.

## 3. `docs/DESIGN_SYSTEM.md` — §2.13 의 금지 규칙을 미니게임까지 넓혀 주세요

§2.13 이 날짜 카드에 대해 이미 적어 둔 문장(`AnimationController` 하나 · `Timer` 금지 —
`pumpAndSettle` 이 통과해야 한다)이 이번에 미니게임에서 **더 나쁜 형태로** 확인됐다.
규격서는 내 소유가 아니라 아래를 요청으로 남긴다. 미니게임 절(§2 의 미니게임 항 또는
§1.10 모션 표 아래)에 규칙 한 덩어리로:

```
- **시간을 어디서 읽는가.** 위젯 안에서 `Stopwatch`·`DateTime.now()` 는 금지다.
  위젯 테스트에서 `Timer` 는 **가짜 시계**를 타고 `Stopwatch` 는 **진짜 시계**를 탄다 —
  한 위젯이 둘을 같이 들면 운영에서는 맞고 **재는 자리에서만 어긋난다**(막대와 마감이
  따로 흐르고, 어긋나는 폭이 기계 부하에 딸려 간다). 판이 스스로 시간 초과로 끝나면서
  전혀 다른 단정("크리티컬! 을 못 찾겠다")으로 터진다.
  - 플레이어가 **흐르는 것을 보거나** 그 값이 **점수에 들어가면** → 프레임
    (`MinigameClock` = `AnimationController`). `animationBehavior: preserve` 필수 —
    기본값은 동작 줄이기에서 길이를 0.05배로 줄이고, **제한 시간은 연출이 아니다.**
    테스트는 애니메이션이 켜진 채로 도니까 어떤 테스트도 이걸 잡지 못한다.
  - 한 번 세고 끝나는 이산 지연(길게 누르기 판정, 물들여 두는 체류, 결과 체류) → `Timer` 로 둔다.
- `pumpAndSettle` 은 **미니게임이 떠 있는 동안 쓸 수 없다.** 시계를 프레임으로 옮겨도
  그대로다 — 티커가 프레임을 예약하기 때문이다. `pump(정확한 시간)` 만 쓴다.
```

§2 의 미니게임 껍데기 항에 한 줄 더:

```
- 남은 시간 막대: `timeLeft` 를 **한 번이라도 준 판에서는** null 이 "숨김" 이 아니라
  "시계가 멈췄다" 다 — 자리를 두고 마지막 값에 멈춘 막대를 그린다. 값을 한 번도 주지 않은
  게임(9종)에는 자리가 생기지 않는다. 예전에는 null 이 오면 자리가 사라져 놀이판이
  **22pt 위아래로 들썩였다**(표정 읽기는 한 판에 네 번).
```

## 4. UI·엔진 담당에게 — 요청 없음

- **UI**: `test/widget/flow_test.dart` 의 우회(`pump(정확한 시간)`)는 **그대로 두세요.**
  시계를 프레임으로 옮긴 것은 결정성을 고친 것이고 `pumpAndSettle` 은 여전히 안 돌아온다.
  §2-2 가 부탁한 막대 자리는 껍데기에서 고쳤다 — 부르는 쪽 세 군데가 아니라 한 곳이다.
- **엔진**: 새 API 는 필요 없다. §2 의 제안도 `game_controller` 가 이미 노출한
  `lastChoice` 만 쓴다.
- **아트·음원**: 새 파일 요청은 §1 의 `choice_crit` 하나뿐이고, 기존 네 개
  (`tap_bad`·`undo`·`timer_low`·`step`)는 `12_audio_handoff.md` §1·§3 에 이미 규격이 있다.
  **사인파 자리표시자는 손대지 않았다** — 가짜 음원을 늘리는 것은 방향이 반대다.
