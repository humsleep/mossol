## 0. 먼저 — 지시받은 과제 1은 **이미 되어 있었다**

지시서의 과제 1은 "`once: true` 개념을 만들라"였는데, **이건 이번 판 전부터 있었다.**

- `lib/engine/models.dart` — `StoryEvent.once`, `once: (j['once'] as bool?) ?? true`
  → **데이터에 칸이 없으면 1회성이 기본**이다.
- `lib/engine/event_engine.dart` `_available` — `if (e.once && s.seen.contains(e.id)) return false;`
  이 함수는 `candidates`(main·crisis·route·hidden) · `dailyPool`(daily) ·
  `openingScriptEvents` 가 **모두 지나는 한 곳**이라 층 구분 없이 걸려 있었다.
- `s.seen` 은 세이브에 있다 → 앱을 껐다 켜도 유지된다.

그래서 **두 번째 1회성 장치는 만들지 않았다.** 대신 없던 것 셋만 채웠다: 소진 방어
검증(§2), 100일 완주 기준의 실측 테스트(§3), 그리고 전 층에서 `once` 가 실제로 지켜지는지
보는 회귀 테스트(§2).

그리고 더 중요한 사실: **`once` 를 더 붙이는 것으로는 재방송이 줄지 않는다.** 산수가 §3에 있다.

## 1. 재방송 — 무엇을 고쳤나

### 1.1 냉각(14일)에 **감쇠**를 얹었다 — `config.repeatWeightPercent` (기본 20)

냉각은 "14일 안에는 안 나온다"까지만 보장한다. **15일째가 되면 이미 여섯 번 본
`d_drink_02`(weight 3)가 한 번도 안 본 weight 1 장면보다 세 배 유리하게** 다시 추첨에 들어간다.
그래서 한 장면이 100일에 일곱 번까지 나왔다.

이제 본 횟수마다 가중치에 20% 를 곱한다. 척도(`EventEngine.repeatWeightScale = 4096`)를
먼저 곱해 정수 나눗셈으로 **다섯 번째 시청까지 구분**한다.

| 본 횟수 | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| weight 1 의 가중치 | 4096 | 819 | 163 | 32 | 6 | 1 |

- **1 이 하한이다** — 감쇠만으로 후보가 비는 일은 없다(빈 하루 방지).
- **후보 전부가 처음 보는 장면인 날에는 척도를 곱하지 않는다.** 곱하면 합계가 4096배가 되어
  같은 `nextInt` 값에서 다른 장면이 뽑히고, 감쇠가 할 일이 없는 날까지 기존 회차·테스트가
  통째로 흔들린다. 미룰 것이 없으면 아무 일도 하지 않는 게 맞다.
- 본 횟수는 새 세이브 칸 `seenCount` 다. **추가만이다** — 칸이 없는 예전 세이브는 빈 맵으로
  읽히고, 그건 감쇠가 꺼진 것과 같아서 예전과 똑같이 굴러간다.
  `once: true` 는 두 번 안 나오므로 **세지 않는다**(세이브가 커지지 않는다 — 지금 데이터에서
  반복 가능한 것은 24개뿐이다).
- 되돌리기(`undoChoice`)도 `seen`·`dailySeenDay` 와 함께 `seenCount` 를 되돌린다.
  안 그러면 되돌린 장면이 '한 번 본 것'으로 남아 부당하게 뒤로 밀린다.

### 1.2 **보충 칸이 재방송으로 분량을 채우지 않는다** — `config.fillSeenBelow` (기본 2)

`planDay` 는 일상을 두 군데서 뽑는다. ① 위기가 없는 날의 일상 칸 ② 하루가
`minEventsPerDay`(3)보다 짧을 때의 보충 칸. ②는 "하트 하나 쓴 보람"을 위해 분량을 맞추는
칸인데, **이미 본 장면으로 채우면 분량은 늘고 보람은 줄어든다.**

그래서 ②는 처음 보는 장면만 쓴다. 단 **오늘 잡힌 장면이 `fillSeenBelow` 개보다 적으면**
재방송으로라도 채운다 — 하트 하나에 장면 하나는 재방송보다 나쁘다.

실측으로 값을 정했다(200일 = f·m 각 100일, 시드 1):

| `fillSeenBelow` | 재방송 평균 | 한 씬 최다 | 하루 평균 씬 | 장면 하나뿐인 날 |
|---|---|---|---|---|
| 99(예전 그대로) | 27.0% | 6회 | 2.86 | 0 / 200 |
| **2(선택)** | **21.0%** | **5회** | 2.66 | **0 / 200** |
| 0(절대 안 씀) | 17.7% | 4회 | 2.53 | **28 / 200** |

0 이 숫자는 제일 좋지만 **200일 중 28일이 장면 하나뿐인 날**이 된다. 하트를 쓰고 한 장면을
받는 날을 만드는 건 재방송보다 나쁜 거래라고 봤다. 값은 `config.json` 한 줄이니 판단이
다르면 0 으로 바꾸면 된다.

### 1.3 결과 — 전후 실측

`test/rerun_share_test.dart`. 시드 1·7·42 × 선호 f/m, 전략 2종 = **100일 완주 6회차**.
지표는 판정문 §1 과 같은 정의다: `(읽은 씬 − 서로 다른 씬) / 읽은 씬`.

| | 개선 전 | 개선 후 |
|---|---|---|
| 재방송 비율 | **25.1 ~ 28.7 %** (평균 27.0%) | **16.2 ~ 23.0 %** (평균 21.0%) |
| 한 회차에 같은 씬 최다 | 6회 | **4~5회** |
| 회차당 읽은 씬 | 290개 | 273개 |
| 재방송이 일어난 층 | 일상 100% | 일상 100% (메인·루트·위기·히든 0) |

판정문이 쓴 23.3~25.7% 와 내 "개선 전" 25.1~28.7% 가 다른 이유는 전략·시드 조합이 다르고,
그 사이에 콘텐츠가 데이터를 고쳤기 때문이다. **같은 코드에서 같은 방법으로 잰 전후만
비교했다** — 테스트가 예전 `config` 번들과 지금 번들을 **같은 실행 안에서** 둘 다 돌린다.

## 2. `once` — 채운 것

### 2.1 소진 방어 검증 — `validate(requireDailyDepth: true)`

`once: true` 를 붙이면 재방송은 사라지지만 **후보도 사라진다.** 일상 전부에 붙이면 후반에는
뽑을 일상이 없어 하루가 메인·루트 둘로 끝난다. `dailyPool` 의 되돌림은 '냉각 때문에 빈 날'만
구제하고 '전부 소진된 날'은 구제하지 못한다.

그래서 **회차마다 반복 가능한 일상(`once: false`)이 `dailyCooldownDays` 개 이상**이어야
한다고 검증한다(냉각이 14일이면 최소 14개). 지금 데이터는 f·m 각 **24개**로 통과한다.

`requireEndingHints` 와 같이 **출시 데이터에만** 켠다(`loadFromAssets`) — 합성 테스트 번들은
이벤트가 몇 개뿐이라 기본은 끈다. 이걸 안 갈라 놨더니 99개 테스트가 깨졌다.

> 넉넉한 선은 하루에 일상을 최대 2개 뽑으므로 **2N = 28개**다. 지금 24개는 그 선에 못 미치고,
> 그래서 후반에 냉각을 뚫는 날이 생긴다. `lint()` 경고로 넣었다가 **뺐다** — 실제 데이터가
> 그 경고에 걸려서 "실제 데이터의 lint 는 비어 있다"는 기존 테스트를 깨뜨린다.
> 출시 데이터가 실패하는 lint 를 남기는 건 lint 를 무의미하게 만든다. 숫자는 여기 적어 둔다.

### 2.2 회귀 테스트

- `test/engine_fixes_test.dart` **F** — daily·crisis·hidden·route **네 층 전부**에서 `once` 가
  이튿날 후보에서 빠지는지, 세이브를 거쳐도 유지되는지, 검증기가 소진을 막는지.
- `test/rerun_share_test.dart` — 100일 완주 6회차에서 **두 번 읽힌 `once` 이벤트가 0개**인지.
  예전 `config` 번들에서도 같이 확인한다(이건 감쇠가 아니라 `_available` 한 줄의 책임이다).

## 3. 10% 에 **못 갔다.** 21.0% 다. 남은 것은 분량이다

목표는 10% 였다. 도달한 값은 평균 21.0%(16.2~23.0%)다. **문턱값을 도달한 값으로 낮춰
통과시키지 않았다** — 테스트 문턱은 25% 이고, 그건 목표가 아니라 **예전 값(25.1~28.7%)과
지금 값 사이를 가르는 회귀 방지선**이다. 주석에 그렇게 적었다.

### 왜 엔진만으로는 안 되나 — 산수

100일 한 회차에서

- 일상 칸이 뽑는 횟수 `D` ≈ **150~174회**
- 트리거를 통과해 **후보로 한 번이라도 올라오는** 일상 종류 `A` ≈ **94~99종**

`D − A` ≈ **50~75회**는 어떤 추첨 규칙으로도 지울 수 없다. 즉 **엔진만의 바닥은 15~19%**이고
(`RerunTally.rerunFloor` 가 회차마다 계산해 테스트가 찍는다), 나는 21.0% 로 그 바닥 근처에 있다.

콘텐츠 담당이 독립적으로 같은 결론에 도달했고(`12_content_handoff.md` §6.2) 동의한다:
**`once: true` 를 어디에 붙여도 `D` 도 `A` 도 안 변하므로 `D − A` 는 그대로다.** 바뀌는 건
같은 횟수의 재방송이 더 적은 장면에 몰린다는 것뿐이고, 14일 냉각에서는 그게 **체감상 더 나쁘다**
(13일 간격이 2~3일 간격이 된다). 실측으로 **D+80 이후에는 조건을 통과하는 `once` 일상이 0개**라
후반 20일의 일상은 전부 반복 풀에서 나온다 — 기준선도 똑같다.

### 10% 로 내리려면

`D` 를 그대로 두고 10% 로 가려면 `A` 가 약 **140종**이어야 한다(지금 94~99종). 길은 둘이다.

| | 필요한 것 | 이벤트 수 |
|---|---|---|
| (a) 일상을 새로 쓴다 | 새 일상 **40~60개** | 늘어난다(테스트 갱신 필요) |
| (b) **한 장면이 여러 대사를 든다** | 상위 20개에 변형 2개씩 = 글 40편 | **안 늘어난다** |

(b) 를 쓸 수 있게 하는 것이 §4다. 작가가 상위 10개에 변형 2개씩만 써도 `A` 가 실효 +20 이 되고,
그만큼 비율이 내려간다. **글은 콘텐츠 담당이 쓰기로 했다** — 엔진 쪽은 §4로 열어 두었다.

## 4. 작가에게 넘기는 도구 둘 (조정자 요청)

### 4.1 `StoryEvent.variants` — 같은 장면, 다른 대사

```json
{
 "id": "d_meet_01",
 "once": false,
 "lines": [ … 원본 … ],
 "variants": [
  { "lines": [ {"who":"narr","text":"또 엘리베이터. 이번엔 눈이 먼저 마주쳤다."} ] },
  { "lines": [ {"who":"narr","text":"세 번째다. 이제 층수는 안 물어봐도 된다."} ] }
 ]
}
```

**고르는 규칙은 회전이다** (`EventEngine.variantOf`). 대사 묶음이 N개일 때

```
보여 줄 묶음 = (회차 시드로 정한 시작점 + 이 회차에 본 횟수) % N
```

- **결정적이다.** 시작점은 `stableSeed(시드, 0, 'variant:<id>')` — 날짜를 섞지 않으므로
  같은 회차에서는 며칠에 보든 같고, 저장·복원 뒤에도 같다. 전 테스트 스위트가 의존하는
  시드 결정성을 깨지 않는다.
- **연속해서 같은 대사가 안 나온다.** 무작위면 두 번째에 또 같은 것이 나올 수 있어 변형을
  붙인 보람이 사라진다. 회전은 N번째까지 반드시 다 다르다.
- **회차마다 첫 대사가 갈린다.** 2회차에 같은 장면을 만나도 첫인상이 같지 않다.
- **세이브 비용 0.** 이미 §1.1 이 넣은 `seenCount` 를 그대로 쓴다.
- 변형이 없으면 원본 그대로 → 지금 데이터는 아무 영향 없다.

**바뀌는 것은 대사뿐이다** — 선택지·효과·조건·알림·삽화·id 는 원본이다. 그래서 작가가
변형을 붙여도 밸런스·루트 순서·엔딩 조건이 흔들리지 않는다.

검증기가 막는 것(`StoryBundle._checkVariants`):

| | 왜 |
|---|---|
| 빈 대사 묶음 | 빈 화면이 된다 |
| `once: true` 에 변형 | 한 회차에 한 번뿐이라 변형을 볼 기회가 없다(낭비) |
| 변형의 사진 줄 유무가 원본과 다름 | `isMoment` 가 회차마다 달라져 하루 계획의 가중치가 흔들린다 |
| 변형 안의 자리표시자 오타 | `displayTexts` 가 변형 줄까지 내놓으므로 `{topp}` 같은 오타가 잡힌다 |

적용 지점은 `EventEngine.viewFor` — **변형을 먼저 고르고 그 위에 MBTI 조건을 거른다**
(순서가 반대면 변형 안의 `mbti` 줄이 안 걸러진다). `GameController.current` 는 넣을 때 한 번만
거르므로 **화면에 뜬 대사가 장면 도중에 바뀌지 않는다**(본 횟수는 `applyChoice` 에서 오르고
그때 그 장면은 이미 끝난다).

### 4.2 `{char:<id>}` — 대사가 특정 인물을 부른다

```text
{char:daeun}                  다은
{char:daeun|이랑랑}           다은이랑
{char:daeun|아야}             다은아
{char:seoyeon|은는|그}        서연은 / (이름을 모르면) 그는
{char:seoyeon,jeongwoo|이가}  서연이 / 정우가   ← 이 회차에 있는 첫 사람
```

조사·호격·존칭·대체어 규칙은 `{name}`·`{top}` 과 **완전히 같은 코드**를 쓴다.

- **없는 id 는 검증 시점에 막는다**(요청대로 런타임이 아니다). `_checkTemplate` 이
  `TextTemplate.charIdsIn` 으로 훑어 `{char:zzz}` 를 `StateError` 로 던진다. 쉼표 목록 안의
  오타도 잡는다.
- 런타임에 이름을 못 찾으면 **id 를 화면에 내지 않고** 중립 명사(`그 사람`)나 대체어로 떨어진다.
- 이름표는 **이 회차에 등장하는 사람만** 담는다(`StoryBundle.charNamesFor`,
  `GameController.runCharNames`). 여성 회차 대사가 남성 쪽 이름을 실수로 부르는 일이 없다.
- 길이 검사(`maxLength`)도 실제 이름으로 잰다. 미리보기 40자 제한이 그대로 지켜진다.

**쉼표 목록은 콘텐츠 요청(§6.1)의 중첩 문법 대체다.** 요청서의
`{char:seoyeon||{char:jeongwoo}}` 는 자리표시자 문법이 중괄호 중첩을 읽지 않아서 쓸 수 없다
(`_token` 이 `\{([^{}]*)\}`). 쉼표 목록이 같은 일을 하고 더 짧다:

```text
[ ] {char:seoyeon,jeongwoo}가 해 줬던 대로 한다
```

## 5. 카운트다운 — 엔진이 내주는 것 (§4-3)

100일 게임이 자기가 며칠째인지 100일 중 4~5번만 말한다는 실측에 대한 엔진 쪽 몫이다.
화면은 UI 담당 것이므로 **값만 내준다.**

| 어디 | 무엇 |
|---|---|
| `GameState.daysLeft(cfg)` | 오늘 이후 남은 날 수. 마지막 날 0, 넘겨도 음수 안 됨 |
| `GameState.isCountdownMilestone(cfg)` | 오늘이 분기점인지 |
| `SaveSummary.daysLeft` · `SaveSummary.countdownMilestone` | **정산·홈 화면이 받는 요약에 이미 들어 있다** |
| `config.countdownMilestones` | `[90, 75, 50, 30, 20, 10, 5, 3, 1, 0]` (config.json, 바꿀 수 있다) |

**축척을 `totalDays - day` 로 잡은 근거는 대본이다.** `m_week1`(D+7)이 "오늘로 D-93",
"93일 남았다"고 말한다 → 100 − 7 = 93. D+1 의 "오늘부터 D-100" 은 구호(제목)이지 계산값이
아니다. 화면이 `D-{daysLeft}` 로 찍으면 대본과 어긋나지 않는다.

`SaveSummary` 에까지 둔 이유: 정산·홈 화면은 `GameState` 를 받지 않고 요약만 받는다.
**UI 담당은 새로 계산할 것이 없다** — `summary.daysLeft` 를 찍으면 100일 중 100일이 된다.

## 6. 저장소의 재방송 계수가 이름과 다른 것을 재고 있었다 (조정자 질문)

**맞다. 확인했고 고쳤다.**

`test/sim_balance_test.dart:774` 는 이랬다.

```dart
if (!e.once) res.dailyRepeatPicked++;
```

`once: false`(= 반복될 수 **있는**) 이벤트가 뽑힐 때마다 센다 — **처음 보는 것도 센다.**
그래서 이 값은 재방송이 아니라 "반복 가능한 풀에서 얼마나 뽑히나"다. 출력 문구
`일상 중 반복(once:false) 비율` 도 '반복 가능'과 '반복됨'이 구분되지 않아
**44.1% → 47.1% 가 재방송 증가로 읽혔다.** 재방송은 늘지 않았다.

고친 것:

- 이름을 `dailyRepeatablePicked` 로 바꾸고, 무엇을 세는지 주석에 적었다.
- **진짜 재방송 계수 `dailyRerunPicked` 를 새로 넣었다**(이 회차에 이미 뽑힌 id 가 또 뽑힌 횟수).
- 출력 문구를 갈랐다:
  `일상 중 반복 가능(once:false)한 것이 뽑힌 비율 50.9% (처음 보는 것 포함 — 재방송이 아니다); 그중 실제 재방송(이미 읽은 씬) 32.5%`
- `sim_balance_test.dart:1240` 의 박힌 분모 `/56` 을 데이터에서 세게 했다(`onceDailyTotal`).
  지금 실제 값은 **101** 이다(조정자가 말한 83 에서 또 움직였다 — 콘텐츠가 작업 중이다).
  이제 숫자를 박지 않으므로 다시 틀릴 일이 없다.

고치고 나서 보인 것 하나 더: **D+100 시점에 `once` 일상 101개 중 약 34개가 한 번도 안 읽힌다**
(`once 일상 미열람 34.8/101`). 트리거·선호·플래그로 걸려 그 회차에서는 나올 수 없는 것들이다.
`A` 를 늘리는 가장 싼 길은 새 글이 아니라 **이 34개의 트리거를 푸는 것**일 수 있다 →
`12_engine_handoff.md` §1.

100일 완주 기준의 제대로 된 재방송 측정은 `test/rerun_share_test.dart` 가 한다.

## 7. 각 테스트가 **예전 동작에서 실제로 깨지는지** 확인한 방법

이 저장소에는 "테스트가 단정문에 도달하지 못한 채 통과한" 이력이 있다(743개 통과인데 실제
오디오 서비스는 스위트에 들어온 적이 없었다). 그래서 새 테스트 하나하나에 대해
**엔진을 되돌려 놓고 깨지는 것을 눈으로 확인했다.** 확인 후 전부 원상복구했다.

| 되돌린 것 | 깨진 테스트 | 출력 |
|---|---|---|
| `config` 를 예전 값으로(`repeatWeightPercent:100`, `fillSeenBelow:99`) | 재방송 비율 | `Expected: less than 0.25 / Actual: 0.2867` |
| `_available` 의 `once` 한 줄 | once 재등장 0 / F 그룹 2건 | `Actual: 0.5525` · `seoyeon_r01×92` 등 36개 재등장 |
| `_weightOf` 의 감쇠 루프 | 가중치 감쇠 | `1번 본 뒤에도 가중치가 안 줄었다: [4096, 4096, …]` |
| `validate` 의 `_checkRepeatables()` 호출 | 소진 방어 | `Expected: throws StateError / Actual: null` |
| `daysLeft` 를 한 칸 어긋나게(`+1`) | 카운트다운 2건 | `Expected: 93 / Actual: 94` |
| `undoChoice` 의 `seenCount` 복원 | 되돌리기 | `되돌렸는데 본 횟수가 남았다 / Actual: 1` |
| `variantOf` 가 원본만 반환 | 변형 2건 | `시드 1: 세 번 보는 동안 대사가 겹쳤다 — [d1 대사, d1 대사, d1 대사]` |
| `_checkTemplate` 의 `{char:}` id 검사 | 없는 캐릭터 지목 | `Expected: throws StateError / Actual: Closure` |

재방송 테스트는 **되돌리지 않아도 스스로 증명한다** — 예전 `config` 번들과 지금 번들을
한 테스트 안에서 둘 다 100일씩 돌려 두 숫자를 같이 찍고, `예전 > 25% > 지금` 과
`평균 차이 > 5%p` 를 단정한다. 엔진을 되돌리면 두 숫자가 같아져서 반드시 깨진다.

  **하루가 비지 않는다**와 **변화가 있다**이므로, "앞 이틀 안에 둘 다 한 번은 나온다"로 바꿨다.
  문턱을 내린 것이 아니라 시드 의존을 뺀 것이다.
