## 0. 먼저 — 콘텐츠가 요청한 엔진 작업 두 개는 **둘 다 들어갔다** ✅

`12_content_handoff.md` §6 에 대한 답이다. **변형 지문 40편을 써 달라 — 지금 쓸 수 있다.**

### 0.1 `StoryEvent.variants` (§6.2 요청) — 됐다

```json
{
 "id": "d_meet_01",
 "once": false,
 "lines": [ … 원본 … ],
 "variants": [
  { "lines": [ {"who":"narr","text":"또 엘리베이터. 이번엔 눈이 먼저 마주쳤다."} ] },
  { "lines": [ {"who":"narr","text":"세 번째다. 이제 층수는 안 물어봐도 된다."} ] }
 ]
}
```

요청서의 모양(`"variants": [[…], […]]`)과 **한 겹 다르다** — 배열의 배열이 아니라
`{"lines": [...]}` 객체 목록이다. 나중에 변형별 `title` 같은 걸 붙일 자리를 남겨 둔 것이다.

지켜지는 것:

- **회전이다.** 원본 + 변형 N개 = N+1 개를 `(회차 시드로 정한 시작점 + 본 횟수) % (N+1)` 로 돈다.
  → 연속해서 같은 대사가 절대 안 나오고, 회차마다 첫 대사가 갈린다. 시드가 같으면 늘 같다.
- **대사만 바뀐다.** 선택지·효과·조건·알림(`preview`)·삽화·id·개수 전부 원본이다.
  밸런스·루트 순서·엔딩 조건에 영향이 없다.
- `variants` 를 안 쓴 이벤트는 지금과 완전히 같다.

검증기가 막는 것(= 붙일 때 주의할 점):

| 막는 것 | 왜 |
|---|---|
| **`once: true` 에 변형** | 한 회차에 한 번뿐이라 변형을 볼 기회가 없다. **반복 가능한 것에만 붙여 달라** |
| 빈 `lines` | 빈 화면이 된다 |
| **변형에만 사진 줄이 있거나, 원본에만 있는 것** | `isMoment` 판정이 회차마다 달라져 하루 계획의 가중치가 흔들린다. 사진 유무는 원본과 같게 |
| 변형 안의 자리표시자 오타 | `{topp}` 같은 것을 `StateError` 로 던진다(원본과 같은 검사) |

**어디에 붙이면 효과가 가장 큰가** — 100일 6회차에서 가장 많이 재방송된 것들이다.

```
d_work_03 · d_kakao_06 · d_kakao_05 · d_kakao_02 · d_misc_04 · d_sns_05
d_meet_07 · d_drink_02 · d_work_01 · d_drink_03 · d_misc_02 · d_date_02
```

상위 10개에 변형 2개씩(글 20편)이면 실효 장면 종류가 +20 이 되고, 그만큼 비율이 내려간다.
산수는 `12_engine_fixes.md` §3 에 있다.

### 0.2 `{char:<id>}` (§6.1 요청) — 됐다. **단, 중첩 대신 쉼표 목록이다**

```text
{char:daeun}                  다은
{char:daeun|이랑랑}           다은이랑
{char:daeun|아야}             다은아
{char:daeun||그 사람}         이름을 모를 때(요청서 문법 그대로 된다)
{char:seoyeon,jeongwoo|이가}  서연이 / 정우가   ← 이 회차에 등장하는 첫 사람
```

요청서의 `{char:seoyeon||{char:jeongwoo}}` 는 **쓸 수 없다.** 자리표시자 문법이 중괄호 중첩을
읽지 않는다(`_token` = `\{([^{}]*)\}`). 대신 **쉼표로 여러 명을 적으면 이 회차에 등장하는
첫 사람**을 쓴다 — 같은 일을 하고 더 짧다.

```text
[ ] {char:seoyeon,jeongwoo}가 해 줬던 대로 한다
```

이걸로 §6.1 이 든 세 곳이 **레코드를 쪼개지 않고** 닫힌다 →
`expect(baseEvents().length, 403)` 을 안 건드려도 된다.

| | 지금 | 이렇게 |
|---|---|---|
| `d_meet_05` "선배가 해 줬던 대로 한다" | 누군지 모른다 | `{char:seoyeon,jeongwoo}` |
| `d_family_02` "조언을 구한다" | 누군지 모른다 | `{char:yeeun,geonwoo}` |
| `m01` "고양이 사진" 의 `name: "알바 동료"` | 이름 없음 | `{char:daeun,haneul}` — **§1 요청 A(쪼개기)를 안 해도 된다** |

- 조사·호격(`아야`)·존칭(`씨`)·대체어 규칙은 `{name}`·`{top}` 과 **같은 코드**다. 새로 배울 게 없다.
- **없는 id 는 출시 전에 `StateError` 로 막힌다.** 쉼표 목록 안의 오타도 잡는다. 오타가 조용히
  '그 사람'으로 새지 않는다.
- 이름표는 **그 회차에 등장하는 사람만** 담긴다. 여성 회차 대사에 `{char:jeongwoo}` 를 쓰면
  이름이 아니라 `그 사람`(또는 적어 둔 대체어)이 나온다 — 남성 쪽 이름이 새지 않는다.
- 선택지 `text`, 말풍선 머리 `name`, 지문, `preview`, `cliffhanger`, 변형 대사 — 화면에 나가는
  글 전부에서 쓸 수 있다. 길이 검사도 실제 이름으로 잰다.

## 1. 안 읽히는 `once` 일상 **34개**의 트리거를 봐 달라 — `assets/story/events_daily.json` (M)

`sim_balance_test` 를 고쳐 놓고 보인 것이다. **D+100 시점에 `once: true` 일상 101개 중
평균 34.8개가 한 번도 안 읽힌다.** 트리거·선호·플래그에 걸려 그 회차에서는 나올 수 없는 것들이다.


출력의 `once 일상 미열람 34.8/101` 줄과 `그날 once 후보` 줄을 같이 보면 된다.
(`그날 once 후보` 가 **D+80·D+100 에 0.0** 이다 — 후반 20일의 일상은 전부 반복 풀에서 나온다.)

## 2. ⚠ `once: true` 를 **10개만 더 붙이면 앱이 안 뜬다** — 경고

소프트락 방어 검증을 넣었다(`validate(requireDailyDepth: true)`, 출시 데이터 로드에서만 켠다).

> **회차마다 반복 가능한 일상(`once: false`)이 `dailyCooldownDays` 개 이상이어야 한다.**
> 지금 냉각은 14일이므로 최소 **14개**.

지금 f·m 각 **24개**다. 여유가 10개뿐이다. 이 아래로 내려가면 `StoryBundle.fromJsonStrings` 가
`StateError` 를 던지고 앱이 뜨지 않는다. 메시지는 이렇게 나온다.

```
여성 캐릭터 회차에 반복 가능한 일상(once:false)이 13개뿐 —
냉각 14일을 버티려면 최소 14개가 필요하다 (부족하면 100일 후반에 일상 칸이 빈다)
```

이건 막기 위한 장치다. **반복을 줄이고 싶으면 `once: true` 를 늘리는 게 아니라 §0.1 의
변형을 붙이는 쪽이다** — `once` 를 늘려도 재방송 횟수(`D − A`)는 그대로이고 더 적은 장면에
몰리기만 한다(콘텐츠 담당이 `12_content_handoff.md` §6.2 에서 낸 산수와 같은 결론이다).

덧붙여, **넉넉한 선은 28개**(냉각 14일 × 하루 최대 2개)다. 24개는 그 선에 못 미치고, 그래서
후반에 냉각을 뚫는 날이 남는다. 28개를 넘기면 `lint()` 에 경고를 되살리겠다.

## 3. 정산 화면의 `D-xx` — **계산할 것이 없다, 그냥 찍으면 된다** — `lib/ui/` (S)

판정문 §4-3 · `12_content_handoff.md` §5 의 1순위. 엔진 쪽은 끝냈다.

`SaveSummary` 에 이미 들어 있다(정산·홈 화면이 받는 그 요약 객체다).

```dart
summary.daysLeft            // 오늘 이후 남은 날 수. 마지막 날 0, 넘겨도 음수 안 됨
summary.countdownMilestone  // 오늘이 분기점인지(크게·색으로 보여 줄 날)
```

- **축척 근거는 대본이다.** `m_week1`(D+7)이 "오늘로 D-93", "93일 남았다"고 말한다 → 100−7=93.
  `D-${summary.daysLeft}` 로 찍으면 대본과 어긋나지 않는다.
  (D+1 의 "오늘부터 D-100" 은 구호지 계산값이 아니다. D+1 에 `daysLeft` 는 99 다.)
- 분기점 기본값: `[90, 75, 50, 30, 20, 10, 5, 3, 1, 0]` — 100일 중 **10일**이다.
  `assets/story/config.json` 의 `countdownMilestones` 로 바꿀 수 있다(내 파일이니 말해 주면 넣는다).
- 회차 도중에도 `GameState.daysLeft(config)` / `isCountdownMilestone(config)` 로 읽을 수 있다.

## 4. `config.json` 에 들어간 새 칸 셋 (참고)

내 파일이라 이미 넣었다. 값을 바꾸고 싶으면 말해 주면 된다.

| 칸 | 값 | 무엇 |
|---|---|---|
| `repeatWeightPercent` | `20` | 본 횟수마다 추첨 가중치에 곱하는 비율(%). 100 = 감쇠 없음(예전 그대로) |
| `fillSeenBelow` | `2` | 하루가 이 개수보다 짧을 때만 보충 칸이 재방송으로 채운다. 0 = 절대 안 씀 |
| `countdownMilestones` | `[90,75,50,30,20,10,5,3,1,0]` | §3 |

`fillSeenBelow` 는 재방송과 하루 분량의 맞바꿈이다. 실측(200일):

| 값 | 재방송 | 하루 평균 씬 | 장면 하나뿐인 날 |
|---|---|---|---|
| 99(예전) | 27.0% | 2.86 | 0 / 200 |
| **2(지금)** | **21.0%** | 2.66 | **0 / 200** |
| 0 | 17.7% | 2.53 | **28 / 200** |

0 이 숫자는 제일 좋지만 하트 하나에 장면 하나인 날이 28일 생긴다. 그 거래를 받을지는
기획 판단이라 2 로 두었다.

## 5. `openingScript` — 아직 비워 두었다

`09_engine_handoff.md` §2 · `12_content_handoff.md` §5 의 재청구다. `config.json` 은 지금도
`"openingScript": []` 다. 이번 작업 지시에 그 항목이 없어서 손대지 않았다.

켜는 것은 한 줄이다.

```json
"openingScript": ["m01", "d_open_bet"]
```

**기다리는 조건 하나**: `m01` 을 `m01`/`m01_m` 으로 쪼개기로 한다면 대본에 둘 다 적어야 한다
(안 맞는 쪽은 `_available` 이 조용히 건너뛴다). §0.2 의 `{char:daeun,haneul}` 로 쪼개지 않기로
하면 지금 목록 그대로 된다. **어느 쪽으로 갈지 알려 주면 그 한 줄을 넣겠다.**

## 6. `tool/transcripts/second_door_transcript.dart` — 아직 안 됐다 (S)

판정문 §0. 하네스가 `queue.insert(0, ne)` 만 해서 컨트롤러(`game_controller.dart` 의
`_queue.removeWhere((e) => e.id == next.id)`)와 다르고, 그래서 **모든 전사의 D+1 에
`d_open_bet`·`d_open_bet_2` 가 두 번 찍힌다.** `tool/**` 는 콘텐츠 담당 파일이라 손대지 않았다.

내 측정 하네스(`test/rerun_share_test.dart` 의 `playFullRun`)에는 컨트롤러와 같은 제거를
넣어 두었다 — 그쪽 코드를 그대로 옮겨 쓰면 된다.

```dart
final ne = engine.byId(next);
if (ne != null) {
  queue.removeWhere((e) => e.id == ne.id);
  queue.insert(0, ne);
}
```

## 7. `test/**` 에 관한 콘텐츠 §4 답

- `expect(baseEvents().length, 403)` — **내 변경으로는 안 움직인다.** §0.2 의 `{char:}` 를 쓰면
  `m01` 을 쪼갤 필요가 없으니 404 로 올릴 일도 없어진다.
- `일상 중 반복(once:false) 비율` 의 오독 — **고쳤다.** 이름을 `dailyRepeatablePicked` 로 바꾸고
  **진짜 재방송 계수 `dailyRerunPicked` 를 새로 넣어** 두 줄로 갈라 찍는다.
  `44.1% → 47.1%` 는 재방송 증가가 아니었다.
- `once 일상 미열람 …/56` 의 박힌 분모 — **고쳤다.** 데이터에서 센다(지금 101).
