## 0. 검증 — 숫자부터

병행 작업자가 같은 나무를 고치고 있어서, **내 변경의 효과는 HEAD 워크트리에서만 주장한다**
(`git worktree add … 9638831`).

| | `flutter test` | `flutter analyze` |
|---|---|---|
| 워크트리 기준선(HEAD `9638831`, 내 변경 0) | **956 통과 · 1 건너뜀 · 0 실패** | 깨끗함 |
| 같은 워크트리 + 내 변경 | **964 통과 · 1 건너뜀 · 0 실패** | 깨끗함 |

늘어난 8개가 아래 §1~§3 의 새 시험이다. 참고로 본 작업 나무(다른 사람들의 진행 중 변경이
실려 있다)에서도 `flutter analyze` 깨끗하고, 미니게임 5개 파일 **89개 전부 통과**,
UI 담당이 우회를 넣어 둔 `test/widget/flow_test.dart` + `debug_gallery_test.dart`
**19개 전부 통과**다.

### 성능은 "느려진 것처럼 보였다" — 재 보니 반대였다

시계를 프레임으로 옮기면 `setState` 가 100ms 마다가 아니라 **매 프레임** 난다. 그래서 먼저
느려졌는지 봤는데, 세션 앞에서 잰 기준선(1분 56초)과 변경 뒤(6분 20초)를 나란히 놓으면
**3배 느려진 것**으로 읽힌다. 그럴싸한 기제까지 있으니 그대로 믿을 뻔했다.

같은 워크트리에서 `git stash` → 실행 → `stash pop` → 실행으로 **연달아** 재니 결과가 뒤집혔다.

| | 테스트 시간 |
|---|---|
| 기준선(stash 됨) | 7분 52초 |
| 내 변경 | **4분 32초** |

느려진 게 아니라 **1.7배 빨라졌다**. 앞의 3배는 그 사이에 다른 에이전트들이 같은 기계에서
스위트를 돌린 부하였다. 공유 기계에서 서로 다른 시각에 잰 두 수치의 차이는 내 변경의
효과가 아니다 — 이건 기록으로 남길 값어치가 있다.

## 1. 한 판에 네 번 들썩이던 판 — 자리를 붙박이로 만들었다

### 지금 무슨 일이 일어나는지 먼저 확인했다

`choice_games.dart` 의 표정 읽기는 답을 공개하는 동안 `timeLeft: null` 을 넣는다.
`MinigameScaffold` 는 `if (time != null)` 로 막대를 그리므로 **자리가 통째로 사라진다.**
증상을 픽셀로 쟀다: 읽어야 할 말풍선의 y 가 **190 → 168**, 즉 **22pt** 위로 뛴다.
문제가 네 개니까 한 판에 네 번, 올라갔다 내려온다.

### 고친 곳은 표정 읽기가 아니라 껍데기다

보고서는 한 게임을 지목했지만 그 `if` 하나가 **12종 전부**를 지배한다. 나머지 11개를 훑어
같은 모양을 두 개 더 찾았다.

| 게임 | `timeLeft` 를 null 로 내리는 때 | 한 판에 몇 번 |
|---|---|---|
| 표정 읽기 (`choice_games.dart`) | 문제마다 정답 공개 550ms 동안 | **4번** |
| 단톡방 대응 (`tap_games.dart`) | 판이 끝날 때 | 1번 |
| 5초 삭제 (`timing_games.dart`) | 판이 끝날 때 | 1번 |

뒤의 둘은 결과 배지가 뜨면서 아래쪽 배치도 함께 바뀌는 순간이라 눈에 덜 띄지만, 같은
`if` 가 같은 일을 한다. 그래서 **부르는 쪽 세 군데를 고치지 않고 껍데기 한 곳을 고쳤다.**

`null` 의 뜻을 갈랐다.

- **값을 한 번도 안 준 판** → 시계가 없는 게임(9종)이다. 자리도 없다.
- **값을 줬다가 null 로 내린 판** → **"시계가 멈췄다"** 다. 자리를 그대로 두고
  마지막 값에 멈춘 막대를 그린다.

`_MinigameScaffoldState._lastTime` 하나로 끝난다. 표정 읽기 쪽에서는 정답 공개 동안
시계를 실제로 세우므로(`_clock.stop()`), 화면의 멈춘 막대가 **거짓이 아니다** —
"지금은 안 흐른다" 를 그대로 보여 준다.

> **자리를 항상 예약하지 않은 이유.** 12_ui_handoff 는 "예약하거나 `Opacity(0)`" 을
> 제안했는데, 그러면 시계가 아예 없는 9종이 세로 22pt 를 영구히 잃는다. 320pt 화면에서
> 22pt 는 선택지 반 칸이다. "쓰기 시작하면 안 없어진다" 가 비용 0 인 쪽이다.

### 시험 (4건)

`test/minigame_games_test.dart`

1. 「표정 읽기 · 답을 공개해도 놀이판이 위아래로 움직이지 않는다」 ← **보고된 증상 그대로**.
   말풍선의 y 좌표를 재서 단정한다. **되돌리면**:
   ```
   Expected: <190.0>
     Actual: <168.0>
   정답을 공개하자 놀이판이 올라왔다 — 한 판에 네 번 들썩인다
   ```
2. 「남은 시간 막대 자리 · 시계를 내려도 놀이판이 움직이지 않는다」 — 껍데기만 놓고
   `timeLeft` 만 갈아 끼운다. **되돌리면**:
   ```
   Expected: exactly one matching candidate
     Actual: _TypeWidgetFinder:<Found 0 widgets with type "AppProgressBar": []>
   timeLeft 가 null 이 되자 막대가 사라졌다
   ```
3. 「멈춘 막대는 마지막 값에 서 있다 (0 으로 떨어지지 않는다)」 — 0.42 에서 null 을 넣고
   막대 값이 0.42 인지 본다. **되돌리면** `Bad state: No element`(막대가 아예 없다).
4. 「시계가 없는 게임(9종)에는 빈 자리가 생기지 않는다」 — **아무도 보고하지 않은 반대쪽**.
   이게 없으면 "자리를 예약해라" 가 "언제나 예약해라" 로 구현되는 것을 막을 게 없다.
   기준선에서도 통과하는 **울타리**다(되돌려도 안 깨진다. 일부러 그렇다).

## 2. 시계가 `Timer` 를 그만뒀다 — 프레임 위로 옮겼다

### 진짜 문제는 `pumpAndSettle` 이 아니라 **시계가 두 개**였다는 것

먼저 기대치를 낮춰 적어 둔다. **`AnimationController` 로 바꿔도 `pumpAndSettle` 은 여전히
돌아오지 않는다.** 티커가 프레임을 예약하는 건 `Timer.periodic` + `setState` 와 똑같다.
그러니 12_ui_handoff §2-1 이 `flow_test` 에 넣은 우회(`pump(정확한 시간)`)는 **그대로
유효하고, 계속 필요하다.** 그 규칙은 지웠다고 생각하면 안 된다.

바뀐 것은 다른 쪽이고, 이게 실제 버그였다.

> 위젯 테스트에서 **`Timer` 는 가짜 시계를 타고 `Stopwatch` 는 진짜 시계를 탄다.**

그래서 예전 코드는 한 위젯 안에 **서로 다른 시계 두 개**를 들고 있었다. 5초 삭제가 가장
선명하다 — 마감(`_readTimer`, `Timer`)은 가짜 시계, 막대(`_sw`, `Stopwatch`)는 진짜 시계다.
운영에서는 둘이 같아서 아무 문제가 없지만, **재고 있는 자리에서만 어긋난다.** 그리고
어긋나는 폭이 기계 부하에 딸려 간다. 12_ui_handoff 가 말한 "판이 스스로 시간 초과로
끝난다" 도, 그것이 "크리티컬! 을 못 찾겠다" 로 나타나 단서가 하나도 없던 것도 여기서 온다.

**점수까지 진짜 시계를 봤다.** 단톡방의 크리티컬 기준은 경과 **6초**고, 5초 삭제의
크리티컬 기준은 **마감의 절반**이다. 씨앗을 고정해도 이 두 판정은 재현되지 않았다.

### 고친 것

`lib/minigames/minigame.dart` 에 `MinigameClock` 하나를 두고 세 게임이 같은 것을 쓴다.

```dart
class MinigameClock extends ChangeNotifier {   // AnimationController 한 개를 감싼다
  double get left;        // 남은 시간 0~1 → MinigameScaffold.timeLeft
  int get elapsedMs;      // 점수를 매기는 자리가 쓴다
  void restart();         // 표정 읽기는 문제마다 되감는다
  void stop();            // 판이 끝났다 / 정답 공개 중
}
```

| 게임 | 예전 | 지금 |
|---|---|---|
| 표정 읽기 | `Stopwatch` + `Timer.periodic(100ms)`, 문제마다 `reset()` | `MinigameClock`, 문제마다 `restart()` · 공개 중 `stop()` |
| 단톡방 대응 | `Stopwatch` + `Timer.periodic(100ms)`, 점수에 `elapsedMilliseconds` | `MinigameClock`, 점수에 `elapsedMs` |
| 5초 삭제 | `Stopwatch` + `Timer.periodic(50ms)` + 별도 `_readTimer` | `MinigameClock` 하나 (마감 = 시계 완료) |

**`AnimationBehavior.preserve` 는 장식이 아니다.** 기본값(`normal`)은 기기에 **동작 줄이기**가
켜져 있으면 길이를 0.05배로 줄인다. 연출이면 맞는 처리인데 이건 **제한 시간**이라, 그대로
뒀으면 접근성 설정을 켠 플레이어의 6초 판이 0.3초에 끝난다. 그리고 **어떤 테스트도 이걸
잡지 못한다** — 테스트는 애니메이션이 켜진 채로 돈다. 규격서 §2.13 이 날짜 카드에
같은 플래그를 적어 둔 것과 같은 이유다.

### 남겨 둔 `Timer` 와 그 근거

전부 바꾸지 않았다. **"시계" 와 "한 번 세는 지연" 을 갈랐다.**

| 남긴 자리 | 왜 |
|---|---|
| 5초 삭제 `_holdTimer` (0.55초 길게 누르기) | 연속으로 **보이는** 값이 아니다. 차오르는 막대는 이미 `TweenAnimationBuilder` 가 프레임으로 돈다 |
| 맞장구 `_timer`(창 열림/닫힘)·`_earlyTimer` | 이산 지연이다. 화면에 흐르는 눈금이 없다 |
| 문장 만들기 `_wrongTimer` | 틀린 카드를 물들여 두는 체류 시간 |
| 껍데기 `_dwellTimer`·`_skipTimer`·`_critTimer` | 결과 체류·건너뛰기 문턱·크리티컬 둘째 박자(90ms) |

이것들은 **원래부터 가짜 시계를 탄다**(위젯 테스트의 `Timer`). 진짜 시계와 섞이는 문제가
없으므로 바꿀 이유가 없고, 바꾸면 티커가 더 늘어난다. **규칙 한 줄로 정리하면**:
*플레이어가 흐르는 것을 보거나 그 값이 점수에 들어가면 프레임, 한 번 세고 끝나면 `Timer`.*
`Stopwatch`·`DateTime.now()` 는 위젯 안에서 금지다.

### 시험 (3건) — **예전 시계로는 통과할 수 없는 것만 골랐다**

판이 그냥 끝나는지만 보는 시험은 두 시계에서 다 통과하므로 아무것도 증명하지 못한다.
그래서 셋 다 **흐른 시간이 pump 한 시간과 같아야만** 성립하는 단정이다.

1. 「5초 삭제 · 남은 시간이 pump 한 시간만큼 줄어든다」 — 1.5초를 흘려보낸 뒤 막대 값.
   **되돌리면**:
   ```
   Expected: a value less than <0.75>
     Actual: <0.9956756756756757>
   1.5초를 흘려보냈는데 막대가 그대로다 — 막대가 진짜 시계를 본다
   ```
2. 「표정 읽기 · 시간이 다 되면 다음 문제로 넘어간다」 — 8초 뒤 같은 문제가 남아 있으면 실패.
   **되돌리면**:
   ```
   Expected: no matching candidates
     Actual: <Found 1 widget with text containing 괜찮아: [Text(""괜찮아 ㅎㅎ 신경 쓰지 마"" …)]>
   시간이 다 됐는데 같은 문제가 그대로다 — 제한 시계가 진짜 시계다
   ```
3. 「단톡방 · 7초를 쓴 판은 순서를 다 맞혀도 크리티컬이 아니다」 ← **점수가 시계를 타는 것을
   못 박는 자리**. **되돌리면**:
   ```
   Expected: false
     Actual: <true>
   7초를 쓴 판이 6초 크리티컬을 받았다 — 경과 시간이 진짜 시계다
   ```

기존 시험 중 깨진 것은 없다. 특히 「눈치 0에서도 2.4초 뒤 길게 눌러 지울 수 있다」(6판)와
「전부 제 순서대로 누르면 크리티컬」이 그대로 통과한다 — 두 번째는 pump 한 시간이 6초
아래라서 여전히 크리티컬이다.

## 3. 3라운드 소리 배선 — 저자가 아닌 사람으로서의 판정

### 3-0. 먼저 읽을 수 있는지: 성공/실패는 갈리고, **성공/크리티컬은 안 갈린다**

글자를 안 읽고 세 결과를 구별할 수 있느냐로 봤다.

| | 소리 | 진동 | 화면 |
|---|---|---|---|
| 성공 | `choiceOk` | `medium` | `surfaceContainerHigh` 바탕 + success 배지 |
| 실패 | `choiceFail` | `heavy` | `errorContainer` 바탕 + danger 배지 |
| 크리티컬 | **`choiceOk` — 성공과 같은 파일** | `medium` + 90ms 뒤 `heavy` | `primaryContainer` 바탕 + brand 배지 |

성공 vs 실패는 세 채널이 전부 다르다. **잘 됐다.** 문제는 성공 vs 크리티컬이다 —
**소리가 같은 파일이고**, 다른 것은 90ms 뒤에 오는 진동 하나뿐이다. 즉 **진동을 끈 플레이어에게
크리티컬은 성공과 소리로 완전히 같다.** 남는 신호는 바탕색 하나(`primaryContainer` vs
`surfaceContainerHigh`)인데, 이건 "글자를 안 읽고" 알아채라고 하기에는 약하다.
게임이 주는 가장 좋은 결과가 가장 약하게 말하고 있다. → 요청으로 보냈다(handoff §1).

### 3-1. 도배되는 큐가 있나 — 하나 있다. 문서가 약속한 것과 다르다

`12_audio_fixes.md` §1 은 `timeLow()` 를 **"판당 한 번"** 이라고 적었다. 코드는 30% 경계를
올라가면 다시 장전되고, **표정 읽기는 문제마다 시계를 되감는다.** 그래서 표정 읽기에서는
한 판에 **최대 4번** 난다. 이 동작 자체는 옳다(문제마다 제 시계가 있으니 문제마다 재촉하는
게 맞다) — 어긋난 건 **문서가 고정한 불변식**이다. 그리고 그 큐가 `callEnd`(통화 종료음,
P1)라서, 전화 화면에서 그 소리를 배운 플레이어는 표정 읽기 한 판에서 "통화가 끊겼다" 를
네 번 듣는다. 이미 요청된 `timer_low` 가 필요한 이유를 하나 더 얹어 handoff §1 에 보냈다.

나머지는 도배가 아니다. `tap()`·`step()`·`undo()` 는 전부 **플레이어가 의도한 한 번의
입력당 한 번**이고, 규칙 3(입력과 결과가 같은 프레임이면 결과만)이 겹치는 자리를 이미
막아 뒀다. 표정 읽기에서 마지막 문제의 `step`/`nudge` 와 결과 큐가 550ms 떨어져 있는 것은
경계선이지만, 두 소리가 실제로 다른 것(문제 채점 / 판 결과)을 말하므로 남겨 둔다.

### 3-2. (a) 헛디딤이 **무음**이다 — 반만 맞다. 반은 내가 고쳤다

**소리를 비워 둔 판단 자체는 맞다.** `choiceFail` 을 빌려 쓰면 "졌다" 와 "틀렸다" 가 같은
소리가 되고, 그건 §3-0 에서 유일하게 잘 된 것(성공/실패 구별)을 망가뜨린다. `choiceFail` 은
P1 + `heavy` 라서, 아직 살아 있는 판의 실수에 붙일 무게가 아니다. 남은 큐를 하나씩 봐도
쓸 만한 것이 없다 — `msgOut`("내가 보냈다"), `waitRead`(전진 큐 그 자체), `callEnd`(통화).
**뜻이 없는 큐를 빌리는 것보다 무음이 낫다.** 그래서 `tap_bad` 요청을 그대로 지지한다.

**그런데 "진동만" 을 최종 답으로 두면 안 된다.** 진동은 플레이어가 끌 수 있고(설정 토글),
iOS 시스템 진동까지 끄면 앱 토글과 무관하게 `HapticFeedback` 이 아무 일도 안 한다.
그러면 헛디딤을 알리는 채널이 **화면 하나뿐**이 된다. 그래서 `nudge()` 8곳을 전부 열어
화면이 무엇으로 대답하는지 확인했다.

| `nudge()` 자리 | 진동을 끈 플레이어가 보는 것 | 판정 |
|---|---|---|
| 문장 만들기 · 틀린 카드 | 카드가 danger 색 + `close` 아이콘(0.6초) + `잘못 고름 1 / 4` 계수기 | 충분 |
| 표정 읽기 · 오답 | 고른 칸 danger + 정답 칸 success, 색·테두리·아이콘 셋 | 충분 |
| 표정 읽기 · 시간 초과 | 정답 칸이 success 로 켜진다 + (이제) 0 에 멈춘 막대 | 충분 |
| 코스 짜기 · 꽉 찬 뒤 헛탭 | `InkWell` 잉크 파문 — `onDimmedTap` 이 콜백을 받으므로 잉크가 **난다** | 약하지만 있다 |
| 단톡방 · 이미 답한 칸 | 같은 잉크 파문 + 그 칸에 이미 `N번째로 답함` 이 적혀 있다 | 충분 |
| 프로필 고르기 · 무응답 | 기록 줄에 `이름 · 무응답` 이 쌓인다 | 충분 |
| 맞장구 · 이른 탭 | 다이얼이 warning 색 + `아직` | 충분 |
| **맞장구 · 놓친 박자** | **아래 박자 줄의 20pt 아이콘 하나. 다이얼은 `…` 로 되돌아간다** | **모자라다** |

마지막 줄이 진짜 구멍이었다. 놓친 박자는 **손가락을 안 댄 사건**이라 화면이 먼저 말해야
하는데, 시선이 붙어 있는 가운데 다이얼은 놓친 순간에도 대기 상태(`…`)로 돌아가서
**아무 일도 없었던 것처럼** 보인다. 28번 등장하는 리듬 게임에서 놓친 박자가
안 보이면 그건 리듬 게임이 아니다.

**고쳤다(소리 없이).** 미리 누른 탭이 `아직` 으로 대답하는 것과 짝을 맞춰, 놓친 박자는
다음 창이 열릴 때까지 다이얼을 danger 색 + `놓쳤다` 로 둔다. 창이 열리기까지의 빈
시간(`_leadMs`, 0.6~1.0초)에 얹으므로 **판의 길이는 한 틱도 달라지지 않는다.**

**시험** — 「맞장구 · 박자를 놓치면 다이얼에 "놓쳤다" 가 남는다」. **되돌리면**:
```
Expected: true
  Actual: <false>
박자를 놓친 순간 시선이 머무는 자리에 아무 말이 없다 — 알림이 진동 하나뿐이라
진동을 끈 손에는 아무 일도 안 일어난다
```

> **새 소리는 하나도 만들지 않았다.** `assets/sfx/` 의 사인파 자리표시자 11개는 의도적
> 유지라고 들었고, 가짜 음원을 하나 더 얹는 것은 방향이 반대다. 필요한 큐는 요청으로만 냈다.

### 3-3. (b) 성패음이 1.5초 사이에 두 번 — **틀렸다. (B) 로 가야 한다**

`12_audio_handoff.md` §2 가 (A) 그대로 / (B) 미니게임을 거쳤으면 건너뛰기 / (C) 더 낮은
큐로 세 갈래를 남겼다. 내 판정은 **(B)** 다. "다른 순간이니까 둘 다 낸다" 는 근거가
이 경우에는 성립하지 않는다.

**이유 1 — 둘째 소리는 새 정보가 0 이다.** 코드를 따라가 보면
`event_screen.dart:1177` 이 `c.choose(index, minigameSuccess: result.success)` 를 넘기고,
`game_controller.dart:1462` 가 그것을 `forcedSuccess` 로 엔진에 꽂는다
(`event_engine.dart:578`: `failed = forcedSuccess != null ? !forcedSuccess : …`).
즉 **둘째 큐의 성패는 첫째 큐가 이미 결정해 놓은 값이다.** 다를 수가 없다. 1.5초 전의
소리로 100% 예측되는 소리는 두 번째 박자가 아니라 **메아리**다. 피드백은 불확실성을
줄여서 제 몫을 하는데, 이 큐가 줄이는 불확실성은 0이다.

**이유 2 — 1.5초는 두 박자로 안 읽힌다.** 이 저장소가 쓰는 두 박자 어법은 **90ms**
(크리티컬)와 **120ms**(엔딩)다. 1.5초는 그 열 배 넘게 떨어져 있어서 "한 사건의 둘째 박자"
가 아니라 "같은 소리가 또 났다" 로 들린다. 그리고 둘 사이에 전면 라우트 전환이 끼어 있어
장면도 끊긴다.

**이유 3 — 빈도.** 회차당 미니게임이 약 150판이다. 즉 회차마다 `choice_ok`/`choice_fail`
쌍이 **150번** 중복된다. 이건 게임에서 가장 많이 듣는 소리를 두 배로 만드는 것이고,
플레이어가 효과음 토글을 내리게 만드는 가장 빠른 길이다. 그리고 그 토글은 전역이라
**나머지 10개 큐까지 함께 잃는다.**

**어느 쪽을 지울 것인가 — 미니게임 쪽을 남긴다.** 미니게임의 결과 큐가
① 플레이어 **자기 손이 만든 판정**의 순간에 나고, ② 크리티컬을 구별하는 유일한 청각·촉각
신호(90ms 뒤 `heavy`)를 들고 있고, ③ 12종이 공유하는 한 자리라 빠뜨릴 수가 없다.
채팅 쪽 큐가 알리는 상태 변화는 답장 글과 수치 변화로 이미 읽힌다.

**(C) 를 왜 안 고르나.** 더 낮은 큐로 바꿔도 "아무 정보 없는 소리를 1.5초 뒤에 한 번 더"
라는 성질은 그대로다. 소리를 낮추는 것은 잡음을 잡음이 아니게 만들지 않는다.

`lib/ui/event_screen.dart` 는 내 소유가 아니라 **손대지 않았다.** 조건 한 줄과, 이미
같은 자리에 있는 선례(`decline` 을 건너뛰는 줄)를 handoff §2 에 적어 보냈다.

## 4. 못 한 것 · 안 한 것

- **`pumpAndSettle` 은 여전히 미니게임 위에서 쓸 수 없다.** §2 에 적었다. 시계를 프레임으로
  옮긴 것은 *결정성*을 고친 것이고, 티커가 프레임을 예약하는 성질은 그대로다.
  `test/widget/flow_test.dart` 의 우회는 유지해야 한다.
- **소리가 들리는지는 이 문서도 증명하지 못한다.** `RecordingSfxService` 는 여전히
  호출만 적는다. §3 의 판정은 전부 **배선과 설계**에 대한 것이고, 실제 음원이 구별되는지는
  실기기 몫이다(`12_audio_fixes.md` §0 과 같은 한계).
- **큐를 하나도 늘리지 않았다.** `tap_bad`·`timer_low`·크리티컬 전용 큐 전부 요청만 냈다.
- **성공/크리티컬의 청각 구별은 못 고쳤다.** `Sfx` enum 이 내 소유가 아니고, 뜻이 맞는
  기존 큐가 없다. 화면 쪽에서 더 세게 말하게 하는 방법도 있지만 결과 배지·바탕색은
  규격서 §2 가 고정한 자리라 혼자 결정할 것이 아니다 — 요청으로 남겼다.
- **문서 수정 요청 한 건.** `12_audio_fixes.md` §1 의 "`timeLow()` 판당 한 번" 은 표정
  읽기에서 사실이 아니다(최대 4번). 그 문서는 다른 사람의 기록이라 고치지 않고 여기에 적는다.
